# Run 012 — Legitimate automated task / API / job markets

Date: 2026-08-15
Status: **COMPLETED**
Stage: machine-executable paid work, API/service marketplaces, agent/inference provider channels, explicit non-bot exclusions

## Objective
Find systems where software can legally perform paid work or expose a machine-callable service with little recurring human input. Distinguish true task/job markets from ordinary SaaS distribution and from human-only microtask sites.

## Executive conclusion
The strongest current versions of the original “bot does tiny jobs forever” idea are not generic microtask websites. They are **metered machine services** where the unit of value is an API call, result, event, inference, monitoring action, automation run, or software seat/usage dimension.

The most directly validated channels in this run are:

1. **Apify Store paid Actors** — strongest literal machine-task fit discovered in this run. A server-side Actor can charge per result/event, including custom events such as processing an item or calling an external API. Revenue is programmatic and recurring once users invoke the Actor.
2. **RapidAPI provider marketplace** — sell API access via pay-per-use, freemium, recurring plans and overages; provider receives customer payments minus marketplace fee.
3. **GitHub Marketplace paid Apps** — build a GitHub App/OAuth App and sell flat-rate or per-unit plans; recurring service is machine-operated after installation.
4. **AWS Marketplace SaaS usage pricing** — sell hosted SaaS and meter users/hosts/bandwidth/data/custom units through AWS billing. Strong B2B channel but seller onboarding/compliance is heavier.
5. **Hugging Face Inference Provider integration** — a real machine-to-machine inference demand channel. Providers expose compatible inference APIs and a billing endpoint; HF routes requests and passes provider pricing through. However provider registration is curated/integration-heavy, not a casual open worker marketplace.
6. **OpenAI GPT monetization** — currently only a small testing cohort of GPT builders is monetized according to current official help documentation. Therefore it is a **RESTRICTED/WATCHLIST** direct-income channel, not a reliable general opportunity.
7. **Zapier public integrations** — useful distribution/retention channel for a paid underlying SaaS/API, but current official partner docs emphasize usage, marketing, support and leads rather than a general per-Zap developer payout. Therefore **not a standalone machine-job income market**.

This run materially strengthens a key project insight: the most durable autonomous model is often to **own the paid machine service** rather than hunt for a website that pays an arbitrary bot to imitate humans.

## 1. Apify Store — paid Actors
Status: **VERIFIED**
Class: SERVER-NATIVE / BUILD-ONCE / machine task marketplace
Automation: **5/5** after reliable publication and monitoring
Paid commodity: event/result/run/output generated by server-side code
Payer: Apify customers invoking the Actor
Revenue source: real customer demand

### Why it matters
Apify explicitly allows developers to publish and monetize automation, scraping and AI-agent Actors. Its current pay-per-event model can charge for specific programmatic events such as creating a result, processing an item or calling an external API. This is unusually close to a legal “tiny paid jobs forever” engine.

### Current economics
Official current formula for pay-per-event Actor profit:

`profit = (0.8 * revenue) - platform costs`

The publishing terms state the developer is generally entitled to 80% of rental / pay-per-result / pay-per-event fees, with platform usage costs potentially deducted depending on configuration.

Current payout docs require billing details, payment method and identity verification. Monthly payout thresholds currently include $20 for PayPal/Wise and $100 for other payout methods.

### Server requirements
Runs on Apify infrastructure rather than requiring our own VPS. This can be even more autonomous than self-hosting, but introduces platform dependence and usage cost.

### Geography/KYC
Identity verification is required for payouts. Azerbaijan-specific payout-method availability still needs a dedicated geography pass.

### ToS/legal boundary
Actors may automate legitimate public/authorized workflows, but the fact that Apify provides crawling infrastructure does not grant rights to scrape or commercially redistribute every target. Each target/source still requires ToS, robots/access, copyright/database-right, privacy and data-license review.

### Scaling constraint
Demand/discovery. Technically an Actor can scale automatically, but paid invocations are not guaranteed.

### Best project forms
- document/file conversion;
- structured extraction where source rights permit;
- data cleansing/transformation;
- monitoring/alerting;
- public-data normalization;
- AI enrichment;
- website QA/testing against owned/authorized targets;
- price/inventory monitoring where target rules permit;
- MCP/agent tools charged by event;
- recurring reports and batch processing.

## 2. RapidAPI — API provider marketplace
Status: **VERIFIED**
Class: SERVER-NATIVE / BUILD-ONCE / API marketplace
Automation: **5/5** after deployment
Paid commodity: API request / subscription quota / overage
Payer: API consumers
Revenue source: real customer demand

RapidAPI official docs support free, pay-per-use, freemium and paid APIs. Paid/freemium plans can combine recurring subscriptions with overage charges.

Current official payout docs state RapidAPI takes a flat **20% marketplace fee** on payments through the Hub; e.g. a $10 subscription yields $8 before any separate payout-processor fees.

### Net model
`Net = 0.8 * customer payments - hosting - upstream API/model/data costs - support - taxes/payout costs`

### Strong fit
A small server can expose a narrow useful endpoint continuously. Good candidates are deterministic transformations, validation, specialized lookup against licensed data, document parsing, monitoring, calculations, format conversion and narrowly scoped AI endpoints whose user price materially exceeds compute/API cost.

### Main risk
Marketplace discovery and commoditization. Many APIs are easy to clone, so differentiated data, workflow integration or superior reliability matters more than code complexity.

### Geography/KYC
Provider payout and Azerbaijan eligibility require dedicated validation; do not assume because developer signup is globally accessible.

## 3. GitHub Marketplace paid Apps
Status: **VERIFIED**
Class: BUILD-ONCE / SERVER-NATIVE B2B software
Automation: **4–5/5**
Paid commodity: subscription/service access, flat rate or per-unit plan
Payer: GitHub users/organizations
Revenue source: real customer demand

Official GitHub docs currently allow paid Marketplace Apps with flat-rate or per-unit monthly/yearly pricing. Paid apps must be owned by an organization and require verified-publisher / financial onboarding.

GitHub currently retains **5%** of transaction income for transactions after January 1, 2021. Current docs also state a $500 monthly revenue threshold before electronic payment is issued at the end of the following month.

### Attractive autonomous products
- repository policy/compliance checks;
- dependency/license alerts;
- release notes / changelog automation;
- issue/PR routing and analytics;
- CI cost/usage monitoring;
- repository backup/reporting;
- secrets hygiene workflows that use authorized GitHub APIs;
- scheduled quality metrics;
- deployment/reliability notifications.

This is not a job market where GitHub assigns arbitrary work. It is a distribution/billing channel for a server-side machine service.

## 4. AWS Marketplace — metered SaaS
Status: **VERIFIED**
Class: BUILD-ONCE / SERVER-NATIVE enterprise SaaS marketplace
Automation: **4–5/5**
Paid commodity: users, hosts, bandwidth, data, tiers or custom metered units
Payer: AWS Marketplace buyers
Revenue source: real customer demand

AWS official Marketplace docs support SaaS products and usage-based pricing. Sellers can meter dimensions such as users, hosts, bandwidth, data, tiers or custom units. Usage is reported through Marketplace metering and billed through AWS.

### Strong fit
This is a route for a mature autonomous B2B daemon/API, especially monitoring, security, infrastructure, data processing or reporting products.

### Constraints
Heavier seller onboarding, product integration, support and compliance than RapidAPI/Apify. Seller/geography eligibility and payout requirements need a dedicated Azerbaijan pass before ranking it as implementable.

## 5. Hugging Face Inference Providers
Status: **RESTRICTED but economically real**
Class: M2M inference provider / API distribution
Automation: **5/5** once integrated
Paid commodity: inference requests
Payer: inference consumers routed through Hugging Face or direct provider accounts
Revenue source: customer usage

Current Hugging Face docs show the Hub routes inference requests to listed providers and charges users at the provider's standard rates without additional HF markup. The provider-registration guide requires implementing compatible task APIs, model mappings and a billing endpoint that reports the cost of routed requests.

### Why restricted
This is not a self-serve “attach one GPU and earn” supplier program. Becoming an Inference Provider requires a real inference service plus integration work and coordination with Hugging Face. Treat it as a channel for a provider business, not a mining node.

### Strategic significance
It validates a broader family: **aggregator-routed inference provider**. A sufficiently optimized inference service can plug into third-party routing/discovery layers and earn per request without direct end-user acquisition for every call.

Status: **RESTRICTED / WATCHLIST**
Class: agent/app marketplace revenue share
Automation: **4–5/5**

Payer: platform revenue-sharing program

Current official OpenAI Help Center says monetization is being tested with only a **handful of GPT Builders**. Therefore a normal builder cannot currently treat GPT Store usage as a dependable direct payout channel.

### Classification
- Publishing GPTs: current and available to eligible paid users.
- Direct GPT usage revenue: not generally open; RESTRICTED.
- Indirect GPT -> owned SaaS/API acquisition: potentially useful but belongs to BUILD-ONCE distribution rather than passive platform payout.

Do not carry forward old 2024 launch promises as if universal monetization exists today.

## 7. Zapier public integrations
Status: **VERIFIED as distribution; REJECTED as direct per-task income market**
Class: integration/distribution channel
Automation: 5/5 for the underlying integration

Current official docs say publishing a public integration has no publication fee and users pay for their own Zapier plans. The Partner Program rewards successful integrations with tiers, support, data and marketing/distribution benefits. Current primary documentation found in this run does **not** establish a general developer payout per Zap task/invocation.

### Therefore
Zapier is valuable if we own a paid SaaS/API and want automated customer workflows to drive product usage. It is not counted here as an independent “Zapier pays our bot for jobs” mechanism.

# 8. Machine-job taxonomy normalized

This run decomposes the broad A12 bucket into these independent economic mechanisms:

1. **Per-event hosted automation marketplace** — customer invokes code; creator earns per event/result (Apify).
2. **API subscription/pay-per-call marketplace** — customer pays recurring fee and/or overage (RapidAPI).
3. **Installed B2B app subscription marketplace** — software reacts to webhooks/events and earns subscription revenue (GitHub Marketplace; Shopify/Atlassian from prior run).
4. **Cloud procurement + metered SaaS marketplace** — enterprise customer usage is metered in infrastructure billing (AWS Marketplace).
5. **Inference routing/provider aggregation** — aggregator routes model requests to provider and passes provider pricing (Hugging Face Inference Providers).
6. **Platform engagement revenue share** — platform may pay based on usage/engagement, but availability can be curated/restricted (OpenAI GPT monetization watchlist).
7. **Distribution-only integration ecosystem** — integration creates demand/retention for our underlying paid product but platform does not inherently pay per task (Zapier).
8. **Self-hosted paid webhook/action service** — not necessarily a marketplace; customers or other agents call our endpoint and pay directly. Stripe usage billing from Run 011 supports the billing primitive.
9. **Authorized data-processing service** — paid extraction/transformation/monitoring where input/data rights are explicitly lawful.
10. **Machine-scored competition/bounty market** — already substantially represented by Bittensor/Apex/Mainframe/solver/prover runs; payout depends on competitive ranking rather than fixed unit price.
11. **Resource execution market** — compute/render/transcode/proof jobs already represented by Golem/Akash/Vast/Nosana/Livepeer/ZK networks; payout is work/resource execution rather than application revenue.

# 9. Human microtask sites — explicit exclusion

Do **not** interpret ordinary survey, CAPTCHA, ad-click, usability-testing, data-labeling, freelance or human-microtask platforms as bot opportunities merely because tasks are repetitive.

Classification rule:
- If the platform buys **human judgment, human identity, human attention, human location or human interaction**, automation is excluded unless official supplier rules explicitly provide a machine/API worker role.
- If automation would fake human behavior, bypass CAPTCHA, misrepresent identity, generate fraudulent engagement, violate site access rules or evade task-quality controls: **REJECTED**.
- A platform can still be relevant on its **requester/developer/provider** side if it explicitly lets developers sell an API/tool/service.

This prevents wasting later runs on “auto-click/captcha/survey bot” schemes that are either prohibited, fraudulent, or structurally dependent on pretending software is a person.

# 11. Economics framework for these markets

For per-call/event services:

`Net/request = selling price - marketplace share - compute - upstream API/model - data-license allocation - bandwidth/storage - payment/tax allocation - expected support/abuse cost`

`Monthly net = successful paid calls * net/request - fixed hosting/monitoring/support`

Break-even calls:

`Fixed monthly cost / positive contribution margin per call`

For subscription apps:

`Monthly net = paying accounts * ARPA * (1 - marketplace fee) - infrastructure - support - upstream services - churn/acquisition cost allocation`

The dominant uncertainty is usually not technical throughput but **paid utilization**. A daemon earning $0.01 per task with no tasks earns zero.
